# Assumptions made

Record of every assumption, interpretation and decision behind the elevator simulation. It is an input to [spec.md](spec.md), to the implementation, and to the README's "assumptions, simplifications, or trade-offs" section, which the PDF requires.

This file is published with the code (M42). The README still carries its own copy of the assumptions, because the PDF asks for them there (R6).

## Status key

- **PDF:** stated directly in `docs/Take_home_Elevator.pdf`.
- **Confirmed:** the user decided this during spec review. Qn is the question number.
- **Accepted:** presented to the user in Round 5 under "Decided without asking". The user raised no objection.
- **Derived:** follows from a confirmed decision or a verified fact.
- **Spec decision:** made while writing the spec to fill a detail. Not put to the user.
- **Plan decision:** made while writing [plan.md](plan.md) to fill a detail. Not put to the user. Ranks the same as a spec decision.
- **Owner's request:** the owner asked for this after the spec review, on the date given. Ranks the same as Confirmed.
- **Owner's decision:** the owner decided this at a gate or review, on the date given. Ranks the same as Confirmed.
- **Confirmed, code review item n:** the owner accepted item n of a code review. Ranks the same as Confirmed.
- **Superseded by X:** a later entry X replaced this one, wholly or in the part named. The text stays as a record, and X holds wherever the two differ.

## Time model

| ID | Assumption | Status |
| --- | --- | --- |
| T1 | One tick equals one floor of travel. Time advances one tick at a time, including ticks when nothing happens. | PDF |
| T2 | Tick order: release requests with `time == t`, assign them in input order, drop off then board at each floor, log positions, then each car moves at most one floor. | Confirmed Q4 |
| T3 | `wait_time = board tick − request time`. `travel_time = drop-off tick − board tick`. `total_time = wait_time + travel_time`. | Confirmed Q4 |
| T4 | Stops always take 0 ticks. There is no stop-time setting, because the PDF doesn't ask for one. This replaces the `stop_ticks` setting agreed in Q4 and the sensitivity pass agreed in Q29. | Confirmed Q36 |
| T5 | A passenger whose car is already at their floor, and is idle or going their way, when they request has a wait of 0. | Confirmed Q4 |
| T6 | With 0-tick stops and LOOK, a car with a rider moves every tick and never reverses, so `travel_time = abs(dest − source)` for every passenger under every algorithm. Therefore `total_time` is `wait_time` plus a constant, and comparing mean `total_time` is the same as comparing mean `wait_time`. Verified on 9,695 random passengers with a throwaway one-car script. | Derived |

## Dispatch and motion

| ID | Assumption | Status |
| --- | --- | --- |
| D1 | Each passenger is assigned to one specific car at the moment of the request. | PDF |
| D2 | Assignments are final. The controller never moves a passenger to another car, even though the PDF restricts only passengers from making changes. | Confirmed Q6 |
| D3 | "Direction logic" means the LOOK rule: a moving car keeps its direction until nothing is left ahead to drop off or pick up, and a passenger boards only if the car is going their way or is idle. This applies to every algorithm. | Confirmed Q7 |
| D4 | The scheduler sees only requests whose `time` is at or before the current tick. | PDF |
| D5 | Every algorithm decides only which car takes a passenger. All cars move by the same LOOK rule, so differences in results come from the assignment choice. | Confirmed Q17 |
| D6 | All implementations must follow the assessment's constraints: immediate and final assignment, no future knowledge, capacity and direction logic. | Confirmed Q17 |
| D7 | The target algorithm is online capacity-aware pickup/drop-off insertion minimising marginal total passenger time. | Confirmed Q15 |
| D8 | Idle cars stay where they are, except under `zone_based`, where they return to the middle floor of their zone. | Confirmed Q19 |
| D9 | Boarding priority when seats are short is a setting, not a fixed rule. There are three behaviours to simulate: strict request order, minimum total time without strict fairness, and weighted fairness. | Confirmed Q18, Q20 |
| D10 | No passenger may wait forever under any behaviour. See D19 for what this guarantees. | Confirmed Q18 |
| D11 | Strict fairness applies per car and direction, because LOOK and final assignments rule out absolute request order. Seats go in request order, and a later passenger boards only if that still leaves a seat for every earlier passenger waiting ahead on that car in that direction. | Confirmed Q26 |
| D12 | The minimum-time behaviour gives scarce seats to the shortest rides, because freeing seats fastest favours the average. The only support found is an analogy to Smith's rule. No elevator study was found. | Accepted Round 5 |
| D13 | Starvation prevention is a configurable mechanism, not one fixed rule. Max wait, max skips and the other methods in D17 are all in scope for testing. | Confirmed Q27, Q34. Superseded in part by M34: only max skips, max wait and seat hold were built |
| D14 | Weighted fairness gives seats to the highest `(1 + weight × ticks waited ÷ floors in building) ÷ ride length`. Weight 0 matches the minimum-time behaviour and larger weights move towards request order. It is simulated at weights 0.5, 1 and 2. `marginal_insertion` applies the same weighting to delays when choosing a car. | Confirmed Q28 |
| D15 | The lineup is `marginal_insertion` (target), `eta` (comparator), and `nearest_car`, `zone_based` and `round_robin` (baselines). Genetic algorithms, MILP, reinforcement learning and the others listed in `algorithm_research.md` are excluded. | Confirmed Q32. Superseded in part by M31: `rush_express` is a sixth algorithm |
| D16 | Under LOOK any set of passengers has only one route, so insertion has no position to search. `marginal_insertion` simulates each eligible car forward with and without the new passenger, then picks the smallest rise in total passenger time. Capacity is included because a passenger predicted to miss a seat shows a longer predicted time. | Confirmed Q33 |
| D17 | Methods in scope for testing: max skips, max wait, seat hold, predicted wait limit, round-trip cap, convex wait cost, lowest worst wait and seat headroom, plus strict order and weighted fairness. Excluded: rejecting requests, moving passengers or sending a second car, jumping a car to an overdue passenger, earliest deadline first, queue freezing and batching. | Confirmed Q34. Superseded in part by M34: predicted wait limit, round-trip cap, convex wait cost, lowest worst wait and seat headroom weren't built |
| D18 | The default guard is max skips of 2 with seat hold on. A labelled no-guard run exists for measurement only and can never be a default. All defaults are our suggestion, not published values. | Confirmed Q34 |
| D19 | "No passenger waits forever" means every passenger is always served, and with seat hold or strict order a passenger's wait is limited to a number of round trips that depends on their place in the queue. No fixed time limit is possible, because requests can't be refused. | Confirmed Q35 |
| D20 | Weighted fairness uses the same guard as minimum time. It does not reserve seats by score. | Accepted Round 5 |
| D21 | `zone_based` splits floors evenly into one zone per car. A request's zone comes from its source floor, or from its destination when the source is floor 1, so up-peak doesn't put everyone on one car. If the zone's car can't serve the trip, the nearest eligible car takes it. | Accepted Round 5 |
| D22 | Ties when choosing a car go to the lowest car number. Ties in boarding go to request order. | Accepted Round 5 |
| D23 | `nearest_car` uses Barney's figure of suitability. An idle car counts as moving toward the call in the same direction. The formula comes from a public README crediting Barney, and the idle rule is our suggestion. | Spec decision |
| D24 | The strict behaviour ignores guard settings, because it satisfies D10 by itself. Outputs record its guard as `none`. | Derived |
| D25 | A seat reservation blocks a passenger only if they would still be aboard when the protected passenger's floor is reached. A rider who gets off first doesn't take that seat. | Spec decision |
| D26 | An idle car with work heads for its oldest waiting passenger. | Spec decision |
| D27 | Under `zone_based`, an express car whose zone middle floor isn't served parks at the nearest served floor, with ties going to the lower floor. | Spec decision |
| D28 | Under strict order, a passenger blocked by a reservation also stops boarding at that floor, so no later passenger overtakes them there. | Spec decision |

## Input

| ID | Assumption | Status |
| --- | --- | --- |
| I1 | The core is a Python function `simulate(requests, config)`, with a CSV loader on top. | Confirmed Q8 |
| I2 | Any invalid row stops the run before it starts, and every bad row is listed. Invalid means a bad or missing field, a floor outside 1..n, a duplicate id, a negative time, or `source == dest`. | Confirmed Q8 |
| I3 | Unsorted rows are sorted by time. Rows with the same time keep file order. | Confirmed Q8 |
| I4 | CSV files are UTF-8, with or without a byte order mark, and must have the header `time,id,source,dest`. | Spec decision |
| I5 | An empty request list is valid. It gives one position row at tick 0, and statistics are `null`. | Spec decision |
| I6 | Each row is one trip by one passenger, because the PDF calls `id` a "Unique passenger ID", so an id can appear only once (I2). A person making two trips needs two ids, and the simulator treats those as unrelated passengers: nothing links the trips, and statistics count two passengers. | Derived |
| I7 | Input must have the right type, in files and through the Python API alike. Times, floors and whole-number settings must be whole numbers, and `true` isn't one. Ids and names must be text. A CSV or TOML file that isn't UTF-8 is invalid. | Confirmed, code review item 4 |
